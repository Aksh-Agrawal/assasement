The teardown fix destroys QML bindings before shutting down the controller and SQLite repository. The previous test queued deferred deletion without explicitly draining the engine's DeferredDelete event. The adjusted test asserts that both launches and teardowns emit no QML engine warnings while retaining the offline review and analytics checks. The Windows Qt suite passed all 41 tests together after using a single test application and consistent offscreen rendering.

The legacy Linux Python 3.11 CI runner segfaulted while processing Qt events. General CI now uses the Python 3.13 release runtime. Python 3.11 with the current PySide6 version remains unverified for the full GUI suite.

Schema 8 remains the minimum installed schema. Version 0.1.1 applies migration 0009, which widens answer storage and preserves existing rows. The migration and rollback tests cover profiles, version-pinned content, attempt answers and pending sync, and verify that newer live rows and credentials survive rollback. Release code, the database, credentials, installed packs and media use separate paths.

## Release artifact and catalog

The disposable `assessment-device-0.1.1.tar.gz` contained 274 files, including all 148 tracked Qt resources. Size was 517,398 bytes. SHA-256 was `a946a1b961a9f49828e090c4991096fa4c3837e2ec7da52e9bc459afbe84657f`. The manifest and `release.json` report 0.1.1, `linux/aarch64`, minimum app 0.1.0 and minimum installed SQLite schema 8. Verification rejected a changed signature, a same-size altered artifact, x86_64, schema 7 and app 0.0.9. The candidate package was signed only with an ephemeral key. The private key, runtime databases, credentials, content caches and generated test reports are outside the release archive and commits.

The isolated cloud catalog rejected a cookie-authenticated upload without Origin with HTTP 403, accepted the signed release with HTTP 201, rejected a duplicate with HTTP 409, and served authenticated discovery and a byte-identical download with HTTP 200. The upload payload was 690,500 bytes. Production readiness returned 200, the device-update and admin settings endpoints required authentication, and the deployed API accepted the workflow's configured frontend Origin in a read-only preflight.

GitHub lists all four repository secret names `UPDATE_SIGNING_PRIVATE_KEY_B64`, `UPDATE_CLOUD_URL`, `UPDATE_ADMIN_EMAIL` and `UPDATE_ADMIN_PASSWORD`. The optional Origin override is unset and the tested default applies. Secret values were not inspected. The production cloud’s trusted key, authenticated upload limit and existing release catalog entries require authorized verification. The checked-in Render blueprint uses an empty default `RELEASE_PUBLIC_KEYS` map, which does not establish the live setting.

GitHub and Git showed no `v0.1.1` release or tag. Production signing and publication did not run.

## Deployment blockers and approval

1. **First OTA from 0.1.0.** Read-only SSH to the Pi timed out. Verify the deployed helper and its systemd umask. If the baseline helper still lacks the permissions fix, approve a maintenance session to replace only the standalone root-owned helper before OTA. The updated release cannot replace the helper until after successful activation. Keep the managed installation and persistent state in place.
2. **Production trust.** Compare the SHA-256 fingerprint of the public key derived from the publishing key with the Pi PEM and Render's `questraa-stable-1` entry. Verify the production admin can read the upload limit and catalog. Use only public fingerprints and keep the private key in its configured secret store.
3. **Publication and physical validation.** Approve the production tag only after those checks. After publication, confirm the workflow's GitHub Release and catalog registration, then verify on-device install, restart, rollback, display/input and retained-data resync in an approved maintenance window.
